# Dreamers · CQA: полное описание системы

Этот документ объясняет, что делает система, как она устроена, как мы её улучшали и почему ей можно доверять. Документ для команды: прочитав его, любой из нас сможет ответить на вопросы жюри.

---

## 1. Что делает система и зачем

**CQA (Conversation Quality Analytics)** оценивает качество работы операторов поддержки Freedom Broker. На вход система получает чат или звонок (расшифровку). На выходе для каждого из 8 критериев чек-листа выдаёт:

- вердикт: «Да», «Нет», «N/A» (неприменимо) или ступень шкалы;
- баллы и общий итог по формуле организаторов;
- короткое объяснение на русском;
- номера сообщений и цитаты, на которых основан вердикт.

**Зачем.** Сейчас проверяющий читает каждый диалог вручную. Система делает первичную оценку за секунды. Человек тратит время только на спорные случаи, а оператор может оспорить любую оценку.

**Языки.** Русский, казахский, английский, включая смешанную речь. Модель оценивает диалог на языке оригинала, без перевода, а цитаты остаются в исходном виде.

---

## 2. Как оценивается один диалог (по шагам)

1. **Импорт.** Сервер забирает набор диалогов из API организаторов (GET по `group_id`) и сохраняет копию ответа на случай, если API станет недоступен.
2. **Нормализация.** Код нумерует сообщения (`m1`, `m2`, …) и переводит время в секунды.
3. **Маскирование.** Код заменяет личные данные метками, например ИИН на `[IIN_1]` и номер карты на `[CARD_1]`. Модель видит только замаскированный текст.
4. **Факты.** Код заранее вычисляет то, что модель легко посчитает неверно: время первого ответа, паузы, смену языка, системные события («личность клиента подтверждена»), подсказки о рисках (сделка в обход компании, оскорбление, чужие данные, внутренняя информация).
5. **Прецеденты.** Код находит похожие диалоги, уже оценённые проверяющими, и для каждого критерия берёт 4 случая с ответом и причиной (подробно в разделе 4).
6. **Инспектор и Адвокат.** Две роли ИИ работают параллельно и независимо (роли описаны в разделе 3).
7. **Проверка ответов.** Код проверяет, что каждая цитата действительно есть в указанном сообщении, что ответ допустим (например, N/A разрешён для этого критерия) и что ступень шкалы существует. Если проверка не прошла, модель получает список ошибок и переделывает только неверные критерии, один раз.
8. **Судья.** Если Инспектор и Адвокат разошлись хотя бы по одному критерию, Судья перечитывает процитированные сообщения и выносит решение. Если они согласны, Судья не вызывается: это экономит деньги.
9. **Уверенность.** Код считает, какая доля ролей согласна с итоговым вердиктом. Высокая уверенность — вердикт принимается автоматически. Низкая или ошибка проверки — диалог уходит в очередь к человеку.
10. **Баллы.** Код (не модель) считает баллы: веса, перераспределение веса при N/A, округление до 0.01 по правилу «половина вверх». Грубая ошибка (c08) ставит отдельный флаг и не меняет баллы.
11. **Сохранение.** Код записывает в базу оценку, все вызовы модели (промпт, ответ, время, токены) и запись в журнал аудита.

Модель вызывается только на шагах 6 и 8. Всё остальное делает обычный код, покрытый тестами.

## 3. Три роли ИИ (панель)

| Роль | Задача | Почему так |
|---|---|---|
| **Инспектор** | Строго применяет критерий: нет явного доказательства — «Нет» и диапазон проверенных сообщений | Не пропускает нарушения |
| **Адвокат** | Ищет самое сильное **честное** доказательство в пользу оператора или N/A, ничего не выдумывая | Не даёт наказать оператора зря |
| **Судья** | Читает оба ответа, перепроверяет цитаты по тексту диалога и решает. В неясном случае выбирает более строгое прочтение | Разбирает настоящие спорные места |

Две противоположные роли, строгая и мягкая, редко соглашаются случайно. Если они согласны, вердикт надёжен. Если спорят, значит, место в диалоге действительно неоднозначное, и туда стоит посмотреть человеку.

Все 8 критериев оцениваются **одним вызовом на роль**. Получается 2–3 вызова на диалог вместо 24.

## 4. Подход 2: «Прецеденты» (финальный)

**Проблема.** С сильной моделью ошибки почти никогда не связаны с непониманием диалога. Модель просто читает правило иначе, чем наши проверяющие. Например: если оператор переспросил то, что клиент уже сказал, это «Нет», а не N/A. Где кончается ступень «7» и начинается «4»?

**Что мы пробовали сначала.** Переписывали формулировки критериев под каждую ошибку. На обучающей половине это помогало, а на отложенной ухудшало результат: формулировка подгонялась под конкретные случаи.

**Решение.** Теперь модель видит 4 похожих случая, которые уже решили проверяющие, с ответом, причиной и процитированными сообщениями. Среди этих 4 случаев обязательно есть примеры с разными ответами, чтобы модель видела, где проходит граница.

**Как ищутся похожие случаи.** Код переводит текст диалога в вектор (эмбеддинг OpenAI) и ищет ближайшие диалоги в базе решённых: 65 размеченных DEV-диалогов и 72 синтетических сценария. Сам оцениваемый диалог в подборку никогда не попадает.

**Результат.** Мы проверили подход на четырёх моделях, и везде он не хуже обычной панели, а на c02 (выявление потребности) заметно лучше:

| Модель | Панель, fresh | Прецеденты, fresh |
|---|---|---|
| Qwen (локальная) | 91.7 % | 92.2 % |
| Kimi-K2.6 | 94.3 % | 95.3 % |
| gpt-6.1-sol | 96.4 % | 96.9 % |
| gpt-6.1-terra | 95.3 % | **96.9 %** |

**Идея на будущее.** Каждое решение проверяющего по апелляции может стать новым прецедентом. Тогда система учится на людях без переписывания промптов.

## 5. Как мы измеряли качество (и почему цифрам можно верить)

Эталонных ответов организаторы не дали, поэтому мы сделали их сами.

| Набор | Что это | Почему ему можно верить |
|---|---|---|
| **Эталон DEV** | Все 65 DEV-диалогов, 520 меток. Размечено **вслепую**: разметчик видел только диалог и чек-лист, без ответа ИИ | 12 диалогов размечены дважды: совпадение 95.8 % |
| **Синтетика** | 72 реалистичных диалога на RU / KZ / EN, в каждом заложена сложная ловушка | Правильный ответ известен по построению, второй человек перечитал каждый |
| **Мутации** | Копия диалога, сломанная специально: убрано приветствие, вставлено оскорбление, данные выданы до идентификации, 5 минут тишины | Нужный критерий **обязан** измениться, безобидная правка не должна менять ничего |

**Правило честной проверки.**
- Все данные разделены на две половины: **TUNE** (на ней улучшаем) и **HOLDOUT** (на ней только измеряем, ошибки не читаем).
- Если улучшение на TUNE не повторяется на HOLDOUT, это подгонка, и мы его откатываем.
- После заморозки системы мы написали ещё 24 **новых** диалога (fresh). Это самая честная проверка.
- Каждое сравнение двух версий — по одним и тем же ячейкам: сколько ответов исправлено и сколько сломано, плюс статистический тест (знаковый тест), чтобы не принять шум за улучшение.

Одна команда `cqa.cli bench` прогоняет всё это и выдаёт метрики: точность по критериям, долю пойманных грубых ошибок, ошибку итогового балла, точность автопринятия, стабильность.

## 6. Итерации: как мы пришли к результату

### 6.1 Промпты и чек-лист (7 версий, модель Qwen на нашем GPU)

| Версия | Что изменили | TUNE |
|---|---|---|
| p1 | Базовая версия | 81.7 % |
| p4 | Температура 0 (одинаковый ответ на одинаковый вход), N/A как явный ответ, факты от кода, «притягивание» цитат к тексту | 85.4 % |
| p5 | Модель сначала пишет обоснование, потом решение; для шкал правило «самая низкая подходящая ступень» | 91.4 % |
| p6 | Флаг безопасности, если модель сама называет нарушение; c08 разбит на 5 конкретных вопросов | 93.3 % |
| p7 | Подсказки о рисках по типам на RU/KZ/EN; уточнённый чек-лист v5 | **95.1 %** |

Что помогло больше всего, по порядку:
1. Обоснование **до** решения: модель «думает», пока пишет.
2. N/A как нормальный, отдельный ответ: распознавание N/A на c02 выросло с 15 % до 82 %.
3. Температура 0: случайные смены ответа упали с 15 % до 0.
4. Конкретные вопросы вместо одного абстрактного критерия.

Проверка на невиданных данных (p1 → p7): HOLDOUT 81.7 % → 92.5 %, fresh 75.0 % → 91.7 %. Значит, улучшение не заучено на TUNE.

## 7. Возможности для пользователя

**Обязательное по заданию:**
- Импорт наборов из API организаторов, оценка всех диалогов одной кнопкой, прогресс выполнения.
- Карточка диалога: вердикт, баллы после перераспределения N/A, разделы, итог, цитаты-ссылки на сообщения. На звонке цитата перематывает аудио.
- Роли «Оператор» и «Проверяющий»: апелляция с комментарием, решение с обязательной причиной, пересчёт итога («ИИ: X → итог: Y»).
- Редактор чек-листа: версии v1, v2, …; замена критерия без кода; применение ко всем диалогам; разница итогов. Повторно оценивается только изменённый критерий, остальное берётся из кэша.
- Выгрузка `results.json` в формате организаторов (кнопка и API).

**Сверх задания:**

| Возможность | Что даёт |
|---|---|
| **Проверка на прочность** | Вставляем в копию диалога нарушение (сделка в обход компании, оскорбление, данные до идентификации, нет приветствия, 5 минут тишины или своя реплика) и смотрим, заметит ли ИИ. Жюри может проверить систему само. |
| **Здоровье чек-листа** | Для каждого критерия: как часто модели спорят и как часто люди отменяют ИИ. Указывает на неясные формулировки. |
| **Тест-драйв критерия** | Новая формулировка проверяется на 5 диалогах до публикации: какие вердикты изменятся, стали ли модели меньше спорить. |
| **Очередь по влиянию** | Неуверенные вердикты отсортированы по тому, на сколько баллов они могут сдвинуть итог. |
| **Где потеряны баллы** | Чипы потерь, крупные первыми; клик ведёт к критерию. |
| **Трасса** | Для каждого критерия видно, что ответила каждая роль, и полный промпт и ответ модели. |
| **Эталон и аналитика** | Точность каждой роли относительно слепой разметки, по языкам и критериям. |
| **Линтер критериев** | Подсвечивает расплывчатые слова в формулировке («хорошо», «правильно», «адекватно»). |

## 8. Надёжность и безопасность

| Риск | Что делает система |
|---|---|
| Модель выдумала цитату | Код проверяет цитату по сообщению; если не прошла, модель переделывает; при повторной ошибке диалог уходит к человеку |
| Одна модель ошиблась | Противоположные роли и Судья; низкая уверенность — проверка человеком |
| Ошибка в подсчёте баллов | Баллы считает только код (Decimal, округление «половина вверх»); есть тесты с эталонными числами |
| Личные данные | Маскируются до отправки в ИИ; ключи и данные остаются на сервере |
| Инструкция внутри диалога («поставь 100 баллов») | Диалог считается данными, а не командой; вердикт всё равно проходит проверку цитат |
| Сбой провайдера ИИ | Автоповтор запросов; кэш хранит готовые оценки; упавшие диалоги можно перезапустить |
| API организаторов недоступен | Копия ответа сохраняется при импорте |
| Неудачный релиз | Каждый релиз в `main` помечается тегом; откат одной кнопкой в GitHub Actions |

Соответствие закону РК об ИИ (с 18.01.2026): ИИ предлагает, человек решает, всё объяснено и записано в журнал.

## 9. Архитектура и разработка

**Стек.** Python 3.12, FastAPI, PostgreSQL 16 (psycopg 3), чистый JS (Web Components, без сборки), Docker Compose, OpenAI API.

**Карта кода.**

| Файл | Что делает |
|---|---|
| `cqa/importer.py` | Импорт и нормализация диалогов |
| `cqa/privacy.py` | Маскирование личных данных |
| `cqa/signals.py` | Факты для модели |
| `cqa/pipeline.py` | Промпты трёх ролей, проверка ответов, уверенность |
| `cqa/precedents.py` | Поиск похожих решённых случаев |
| `cqa/llm.py` | Единственное место, где вызывается модель |
| `cqa/scoring.py` | Вся математика баллов |
| `cqa/evaluations.py` | Оценка, кэш, апелляции, решения, прогоны |
| `cqa/bench.py` | Измерение качества |
| `cqa/results.py` | Выгрузка `results.json` |
| `web/` | Интерфейс |

**Как мы работали.**
- 4 направления (импорт, движок ИИ, интерфейс, качество), у каждого свой владелец.
- Две среды: ветка `dev` разворачивается на тестовый стенд, `main` — на прод. Деплой автоматический после тестов.
- Перед каждым изменением промпта или чек-листа — прогон бенчмарка и сравнение с предыдущей версией.
- Все решения записаны в `docs/DECISIONS.md`, все замеры — в `docs/EVALUATION.md`.

**Удобство разработки.** Режим `mock` (фальшивая модель) позволяет запускать систему и тесты без ключа API.
